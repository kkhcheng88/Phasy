# 3D Muscles in a Phone Browser — Research Notes

## 1. Summary

- Data: use the official **BodyParts3D 4.3 OBJ set** (DBCLS, CC BY 4.0 — see `anatomy-sources.md`), 3,210 meshes identified by FMA IDs, fetched via the official Anatomography/LSDB endpoints, not a stale CC BY-SA mirror. [olivercase/body_parts_3d_api](https://github.com/olivercase/body_parts_3d_api)
- Skip Z-Anatomy for v1: its only advantage (cleaned, layer-grouped, Wikipedia-named meshes) is real but its distribution is a 300–630 MB Blender file (unverified exact figure, see §3) requiring a Blender export step, and it adds a CC BY-SA 4.0 share-alike duty on any adapted mesh we ship.
- Pipeline: Blender/`gltf-transform` → per-muscle GLB → **merge into one mesh with a per-vertex/per-submesh muscle-id attribute**, Draco or Meshopt compression, target well under mobile triangle/draw-call budgets (§7).
- Library: **three.js**, using `Raycaster` for tap-to-select and per-submesh materials for status colour and layer show/hide; richest low-level control of the three candidates (§6).
- Reference implementation to study first: [nqwrc/3d-anatomy](https://github.com/nqwrc/3d-anatomy) — three.js viewer already built on the Z-Anatomy/BodyParts3D dataset, GLB + Draco, per-structure `za_name` extras.

## 2. BodyParts3D facts

- **Download location (official)**: DBCLS LSDB Archive download page, https://dbarchive.biosciencedbc.jp/en/bodyparts3d/download.html — offers ID/name text tables plus polygon-mesh archives in **OBJ format** organised two ways (IS-A Tree ≈136 MB zip, PART-OF Tree ≈62 MB zip); the page itself states the meshes use a **"99% polygon reduction rate"** (i.e. heavily decimated from source scan data), exact per-mesh triangle counts not stated on the page (unverified).
- **ID scheme**: each mesh/"representation" carries a **BodyParts3D representation ID** mapped to a **FMA (Foundational Model of Anatomy) concept ID**, plus English/Japanese names in the accompanying text tables (IS-A: https://dbarchive.biosciencedbc.jp/en/bodyparts3d/data-1.html ; PART-OF: https://dbarchive.biosciencedbc.jp/en/bodyparts3d/data-2.html).
- **One file per muscle / left-right split**: the community re-packagings confirm one mesh file per anatomical part. [olivercase/body_parts_3d_api](https://github.com/olivercase/body_parts_3d_api) states its **3,210 `.obj` meshes are "every FMA-mapped organ, muscle, bone, blood vessel, nerve, cartilage"**, i.e. one mesh per FMA-mapped structure — FMA already distinguishes left/right instances, so left and right muscles are separate meshes/IDs. The older [Kevin-Mattheus-Moerman/BodyParts3D](https://github.com/Kevin-Mattheus-Moerman/BodyParts3D) mirror repackages ~940 named structures as individual binary STL files (converted from OBJ "since these are significantly smaller in size") with a `parts_list_e.txt`-style table mapping FMA IDs to English names, from data version 20110915 (chosen over v4.0 because "version 4.0 appears to have intersecting skin/muscle areas" per that repo's own notes — i.e. a known geometry defect in a later official release, unverified against DBCLS directly).
- **Total number of muscle parts / total muscle-set size**: **unverified precisely.** The official download bundles are whole-body (bones + organs + vessels + muscles together, ~136 MB / ~62 MB zipped for the two tree variants), not muscle-only; olivercase's repo total is 3,210 meshes across *all* structure types, and it does not state a muscle-only subcount or a muscle-only total file size in the fetched excerpt. Do not use "3,210" as a muscle count — it is the whole-body structure count.
- **Mesh quality / known gaps**: no official Khronos-style polygon-count table found for BodyParts3D specifically. Known defect: v4.0 has intersecting skin/muscle geometry per the Kevin-Mattheus-Moerman repo's stated reason for staying on v3.0/20110915 (https://github.com/Kevin-Mattheus-Moerman/BodyParts3D) — **unverified directly against a DBCLS changelog**, flag for re-check before picking a data version.
- **Formats other than OBJ**: unverified in this pass whether DBCLS still also offers VRML/Collada (earlier anatomy-sources.md note); current official download page as fetched shows OBJ only.

## 3. Z-Anatomy facts

- **What it adds over BodyParts3D**: cleaned/re-topologised meshes, muscles grouped and named by system/layer, Wikipedia-sourced text definitions, and a maintained **Blender template** (`Z-Anatomy/The-blend` repo) with a `TA2.csv` terminology file and an `Anatomy-shortcuts.py` navigation script. https://github.com/Z-Anatomy/The-blend
- **Download location**: GitHub org https://github.com/Z-Anatomy (repos `The-blend`, `Models-of-human-anatomy`) and the standalone app distributed via itch.io (per `anatomy-sources.md` §3.2, not re-verified here).
- **Size**: figures found conflict and are **unverified as a single authoritative number** — one third-party downstream repo describes a full Z-Anatomy Blender source file at **630 MB** (kept out of that repo's own git history, "gitignored"), while a separate mirror site lists a `Startup.blend` of **291 MB** for Blender 3.6. Treat as "several hundred MB" until confirmed directly from `Z-Anatomy/The-blend`.
- **Per-part export**: confirmed possible. A downstream project's own notes (cited via search, not an official Z-Anatomy doc) describe the export convention: objects whose names end in `.j`/`.g` are text-label helpers and are skipped, meshes with ≤1 polygon are muscle-insertion markers and are skipped, and the real export path is "select the collection for one system → export GLB with `export_extras=True` (to keep the `za_name` custom property), `export_apply=True`, and Draco compression" — i.e. Blender's own glTF exporter, not a bespoke tool. One such export: a Draco-compressed muscle GLB went from 16.2 MB → 3.3 MB after compression, split into 281 separate meshes for one system.
- **License duties for our use**: already researched in `anatomy-sources.md` §3.2 — CC BY-SA 4.0; ShareAlike attaches only to an *adaptation* of the model, not to bundling it unmodified — not repeated in full here per the task instruction.

## 4. Id-to-name mapping

- **Official**: DBCLS's own ID/name tables are the primary source — "Table of 3D organ model IDs and organ names" for both the IS-A Tree (https://dbarchive.biosciencedbc.jp/en/bodyparts3d/data-1.html) and PART-OF Tree (https://dbarchive.biosciencedbc.jp/en/bodyparts3d/data-2.html) hierarchies; these map BodyParts3D representation IDs to FMA IDs and English/Japanese names, per the download page.
- **Community re-publications**: [Kevin-Mattheus-Moerman/BodyParts3D](https://github.com/Kevin-Mattheus-Moerman/BodyParts3D) ships `.txt` files in its `assets` folder pairing FMA IDs with plain English names; [olivercase/body_parts_3d_api](https://github.com/olivercase/body_parts_3d_api) validates its 3,210 meshes against an authoritative manifest file it calls `FMA2Obj.txt` (FMA-to-OBJ mapping) plus "FJ IDs" (its term for DBCLS's internal model-component IDs) and "BP IDs" (BodyParts3D representation IDs) — i.e. a three-way ID crosswalk (FJ / BP / FMA) plus English names, obtained from DBCLS's own Anatomography viewer endpoints.
- **FMA → Wikidata / OpenStax names**: no single published FMA→Wikidata crosswalk table was located in this pass (**unverified / not found**); `anatomy-sources.md` §3.7 already documents that Wikidata carries muscle-specific properties (P3490 origin, P3491 insertion) and that FMA cross-references exist in OBO/BioPortal format, but a ready-made FMA-ID→Wikidata-QID table for muscles specifically was not directly located — building one would likely mean joining FMA IDs to Wikidata via Wikidata's own FMA-ID property (unverified property number) or via Uberon as an intermediate ontology (CC BY 3.0, cross-referenced with FMA per `anatomy-sources.md` §3.7).

## 5. Conversion pipeline

- **OBJ → glTF/GLB**: standard tool is **glTF-Transform** (`gltf-transform`, MIT-licensed CLI/library, https://gltf-transform.dev/), which reads OBJ and writes GLB, and applies compression/optimisation passes in the same tool.
- **Mesh compression**:
  - **Draco** (`KHR_draco_mesh_compression`) — for geometry-heavy models (>1 MB) can cut file size by roughly 95%; two modes, `edgebreaker` (higher compression, reorders vertices) and `sequential` (preserves index order). https://gltf-transform.dev/modules/extensions/classes/KHRDracoMeshCompression
  - **Meshopt** (`EXT_meshopt_compression`) — "recommended for anything running in a browser" per gltf-transform's own guidance cited in search results, reaches sizes comparable to Draco but decodes several times faster, which matters because decoding happens on the user's loading screen; a mesh-heavy model with no compression often drops 60–80% in size with Meshopt alone. Source: gltf-transform.dev / meshoptimizer.org (https://meshoptimizer.org/gltf/) — **exact wording paraphrased from a WebSearch summary of gltf-transform.dev, re-check the page directly before quoting numbers in a spec.**
  - Confirmed real-world case (Z-Anatomy downstream): one Draco-compressed muscle-system GLB went from 16.2 MB → 3.3 MB.
- **Mesh simplification**: lossy — "removes triangles which is visible at aggressive settings" (gltf-transform.dev, via search summary — re-verify wording on-page). `gltfpack` (part of meshoptimizer, https://meshoptimizer.org/gltf/) is the standard CLI for combined simplification + Meshopt compression.
- **Realistic phone target size**: no single official number found for "a full labelled muscular system on a phone." Working budget, triangulated from §7's mobile triangle-budget figures (30–50k on-screen triangles for 60 fps) plus the Z-Anatomy downstream example (one system, Draco-compressed, at 3.3 MB): **a first-pass target of a few MB total (compressed) for the visible muscle layer, built up system-by-system rather than loading all ~600+ muscles at once** — this is a reasoned estimate, not a cited spec, and should be validated against an actual export before committing to a number in a ticket.

## 6. Library comparison

| | three.js | Babylon.js | `<model-viewer>` |
|---|---|---|---|
| Tap-to-select (picking) | `Raycaster` class, official manual page and API docs: https://threejs.org/manual/en/picking.html , https://threejs.org/docs/pages/Raycaster.html — `setFromCamera()` + `intersectObjects()`, returns ordered hits; CPU-based, can pre-filter with bounding volumes. | Built-in scene picking, official docs: https://doc.babylonjs.com/features/featuresDeepDive/mesh/interactions/picking_collisions — ray/collision based mesh picking is a first-class engine feature. | `positionAndNormalFromPoint()` returns a surface hit point + normal for a screen point (official method, https://modelviewer.dev/docs/#entrydocs-annotations-methods-positionAndNormalFromPoint per search results) but there is **no confirmed official API to resolve a tap directly to a named mesh/node** — a known open issue exists where the hit can land on a base plane instead of the model surface (google/model-viewer#3531). Treat "tap → identify which muscle" as **not natively solved** by model-viewer.
| Per-mesh colour / material control | Full control: any `Mesh.material` can be swapped per-object; standard three.js pattern, no special doc needed beyond material API. | `MultiMaterial` (official API: https://doc.babylonjs.com/typedoc/classes/BABYLON.MultiMaterial) lets one mesh carry an ordered list of `subMaterials` mapped to submeshes — designed exactly for "one mesh, many coloured parts." | `material-variants` (`KHR_materials_variants`) lets you pre-bake named material sets and switch the whole model to a variant via the `variantName` attribute (https://modelviewer.dev/examples/scenegraph/) — good for swapping a *whole model's* look, not naturally per-muscle *runtime* recolouring (status colours would need to be pre-baked as variants or manipulated via the scene-graph API, less documented).
| Show/hide by layer | Native: toggle `object3D.visible` per mesh/group. | Native: toggle `mesh.isVisible` / `setEnabled()` per mesh; engine designed for large interactive scenes. | Limited/unverified: model-viewer's scene-graph API is newer and less documented for bulk visibility toggling of named nodes; no official example located for "hide muscle layer" pattern in this pass. |
| Smooth rotation on mid-range phones | Depends entirely on our own render-loop and asset budget; three.js has no built-in device-tier detection. | Same; Babylon.js is a heavier engine (physics, more built-ins) which is unused overhead for this use case unless we need those features. | Camera orbit controls are built in (`camera-controls` attribute) and tuned by Google for broad device support, but internal render/material control is the weakest of the three for this app's core interaction (tap-select-and-recolour hundreds of named parts). |
| Overall fit for Phasy | **Best fit**: lowest-level control over exactly the two things this app needs (raycasting to a specific mesh, per-mesh material), smallest runtime, most examples/community code for anatomy-style viewers (see §8). | Strong second choice, arguably more "batteries included" than needed for a single interactive body; valid fallback if three.js raycasting against 100s of meshes becomes a bottleneck team doesn't want to hand-optimise. | Fastest to a demo (drop in a GLB, camera controls for free) but weakest for the specific "tap this muscle, recolour it, hide this layer" feature set — real gaps around per-mesh hit identification and bulk visibility, both **unverified as solved without extra custom code**. |

## 7. Performance guidance

- **Triangle budgets (mobile)**: figures found via search summary (blog sources, not a single Khronos page fetched directly — mark as **weaker citation, re-verify before using in a spec**): mid-range Android devices reportedly sustain 60 fps with a full-scene budget around **~50,000 on-screen triangles**; a mobile "hero" asset is commonly targeted at **1,500–5,000 triangles**; a WebGL product-hero model is commonly targeted at **5,000–25,000 triangles** depending on scene complexity. Source citations: https://blog.neural4d.com/user-guide/polygon-count-for-3d-game-assets-printing-and-webar/ and https://blog.4dpipeline.com/the-khronos-2.0-guidelines-that-actually-fix-web-3d — **neither is an official khronos.org page**; the second blog references "Khronos 2.0 guidelines" and the **Khronos Asset Auditor** tool (which does ship official per-use-case budget profiles — desktop web / XR / mobile AR — per that blog's description) but the official Khronos source for that tool was not directly fetched in this pass. **Mark these numbers "unverified against a primary Khronos source."**
- **Draw call budget**: commonly cited threshold for stable 60 fps in desktop WebGL is **under ~500 draw calls per frame**, with mobile browsers needing a lower number (exact mobile figure not given) — same weak (blog) sourcing as above, **unverified against a primary source**.
- **Hundreds of separate meshes — is it a problem, and the fix**: yes, per both Babylon.js's own community/forum guidance and general WebGL practice, each separate mesh is (at minimum) one more draw call and one more JS-side scene-graph node to traverse; the standard fix cited is **merging static geometry into fewer draw calls while keeping per-part identity via a vertex attribute or submesh material index**, e.g. Babylon.js `Mesh.MergeMeshes` combined with `MultiMaterial` submeshes (one real forum example: merging cut draw calls from 207 to 67 by combining same-material meshes — https://forum.babylonjs.com/t/merged-meshes-multimaterials-and-draw-call-counts/23113, a community forum post, not official docs — **cite with that caveat**). Babylon's own `MultiMaterial` API doc frames this directly: "A multi-material is used to apply different materials to different parts of the same object without the need of separate meshes... This can be used to improve performances." https://doc.babylonjs.com/typedoc/classes/BABYLON.MultiMaterial — this is the officially documented version of the "merge meshes, keep per-part ids via submesh material index" pattern needed for Phasy's hundreds of muscles.
- **Net implication for Phasy**: do not load ~600+ individual muscle meshes as ~600+ separate three.js/Babylon objects. Merge per visible layer (or per body region) into fewer meshes carrying a per-vertex/submesh muscle-id, and raycast against the merged mesh then resolve the hit triangle/submesh back to a muscle id — this is the standard fix, not a Phasy-specific invention, per the Babylon.js official `MultiMaterial` doc above.

## 8. Existing viewers

- **[nqwrc/3d-anatomy](https://github.com/nqwrc/3d-anatomy)** — "Interactive 3D atlas of human anatomy — 2,800+ structures across seven systems," built on the **Z-Anatomy dataset**, rendered with **three.js** + WebGL, models as **GLB with Draco compression**, one GLB per anatomical system, uses a custom `za_name` glTF-extras property to preserve Z-Anatomy's own names (since the standard glTF exporter can rename objects), shares materials across meshes and clones only when a mesh needs individual recolouring (i.e. already implements the "per-mesh status colour without one material per mesh" pattern Phasy needs), deployed via GitHub Actions to GitHub Pages. **License: CC BY-NC-SA 4.0** (non-commercial) — stated reason given in the repo is two non-commercial source components (inner ear and kidney) pulling the whole distribution to NC — **this makes the repo's code/approach fine to learn from, but its packaged GLB assets are not usable in a commercial Phasy build without re-deriving a CC-BY-only asset set.** Directly relevant as an architecture reference for our own three.js pipeline.
- **[jaydenpcastro-ship-it/z-anatomy-atlas](https://github.com/jaydenpcastro-ship-it/z-anatomy-atlas)** — "Interactive 3D human anatomy atlas built from the Z-Anatomy Blender model (three.js, static site)" — found via search, **not independently fetched/verified in this pass**; same technology pattern (three.js + Z-Anatomy) as nqwrc's repo, worth a second look but license/currency **unverified**.
- **[olivercase/body_parts_3d_api](https://github.com/olivercase/body_parts_3d_api)** — not itself a viewer, but the most directly useful **data-acquisition tool**: downloads and verifies the full official 3,210-mesh BodyParts3D 4.3 OBJ set against DBCLS's own manifest, plus a "selector for named subsets." Repo code MIT-licensed; downloaded anatomical data still carries BodyParts3D's own DBCLS license terms (confirm CC BY 4.0 vs CC BY-SA 2.1 Japan depending on which release the tool actually pulls — see the version-drift risk already flagged in `anatomy-sources.md` open question 7).
- **[Kevin-Mattheus-Moerman/BodyParts3D](https://github.com/Kevin-Mattheus-Moerman/BodyParts3D)** — older static mirror (binary STL, ~940 named structures, DBCLS 2011 data version), useful only as a name/FMA-ID reference table, not as a web-viewer example; **carries the older CC BY-SA 2.1 Japan license**, so do not pull mesh geometry from this specific mirror for a share-alike-free build.
